# Feature Specification: Device Capability Probe, Capabilities Matrix, and Capability-Aware API Surfacing

**Feature Branch**: `008-capability-matrix`
**Created**: 2026-06-13
**Status**: Draft
**Input**: Umbrella architecture work from issue #123. The library has accumulated enough evidence of device-class and firmware-version variation in the Akuvox HTTP API (X916, E18C, X915S, IT83) that we can no longer treat all devices as a single capability surface. This feature introduces (1) a non-destructive capability probe, (2) a curated in-library capability matrix keyed by device class and firmware band, (3) capability-aware surfacing of operations through fail-fast errors and adapter dispatch, and (4) a refactor of currently-scattered field-name aliasing and schema-shape branches onto the matrix. Folds in #118 (closed), #119 (closed), #121, #122, and the `ScheduleRelay` / `Schedule-Relay` / `Schedule` aliasing work tracked in #99 / PR #101 (see also `specs/006-schedule-relay-compat/` for prior design lineage).

## Background and Evidence

Five device/firmware combinations have driven this work:

| Device | Firmware | Observed behavior |
|---|---|---|
| X916 | 916.30.10.114 | Baseline. `/api/*` works. `add_user` accepts `ScheduleRelay`. |
| E18C | 18.30.11.21 | `add_user` requires hyphenated `Schedule-Relay`; un-hyphenated returns `retcode: -1`. (#99 / PR #101.) |
| X915S | 2915.30.10.113 (old) | `add_user` returned HTTP 500 for any payload. Resolved by firmware update (#119, closed). |
| X915S | 2915.30.10.114 (current) | User read uses `Schedule` not `ScheduleRelay` (#118 / PR #120). Contact schema is apartment-book style with `APTName`, `APTNum`, `Building`, `Landline`, no `ID` field (#121). Contact writes return `unsupported action`. |
| IT83 | 83.30.10.4 | `/api/relay/*` returns "No handlers for this request". Local relay must be triggered via `/fcgi/do?action=OpenDoor` (#122). User/contact write paths likely also unsupported. |

These cluster onto four orthogonal axes of variation:

1. **Endpoint availability** — entire `/api/*` namespaces missing on indoor monitors; alternate `/fcgi/*` endpoints needed.
2. **Field-name aliasing** — `ScheduleRelay` vs. `Schedule-Relay` vs. `Schedule` for the same logical field.
3. **Schema shape** — door-phone vs. apartment-book contact models; users with vs. without `Building` / `Room` / `EffectiveType`.
4. **Action availability** — endpoint exists for read but rejects writes (`unsupported action`).

Treating each combination as a one-off fix has not scaled. This specification describes the structural change that lets the library handle additional device classes and firmware bands as localized matrix updates rather than scattered conditional branches.

## User Scenarios & Testing *(mandatory)*

User stories are ordered to mirror the four-phase split called out in issue #123: each phase is independently shippable, delivers user-visible value on its own, and unlocks the next phase.

### User Story 1 - Probe an unfamiliar device safely (Priority: P1) — Phase 1

An integrator who has just acquired a new Akuvox device — or whose existing device just took a firmware update — needs to learn what the library can do against it before writing provisioning code. They invoke a single library call, `await device.probe_capabilities()`, and receive a structured report describing which logical operations are supported, which field-name variants the device accepts, what schema shape its list endpoints return, and which behaviors are unknown. The probe completes without creating, modifying, or deleting any data on the device, and without firing any relays.

**Why this priority**: This is the foundational capability the rest of the work depends on. With the probe in hand, the integrator can already make sound decisions for an unfamiliar device even before the matrix and surfacing layers exist; without it, every subsequent layer is guessing. Phase 1 introduces the probe and the data structure it returns, but does not yet change behavior for existing callers.

**Independent Test**: Point the library at a previously-uncharacterised Akuvox device, call `probe_capabilities()`, and confirm (a) the call completes without raising, (b) the returned report enumerates which read operations succeeded and which failed and how, (c) no users, contacts, schedules, or relay events were created or fired during the probe, and (d) running the probe a second time produces the same report.

**Acceptance Scenarios**:

1. **Given** an unfamiliar device that responds to `/api/system/info`, **When** the integrator calls `probe_capabilities()`, **Then** the library returns a capabilities report containing the device class, firmware version, a per-capability status profile (each capability the probe touched is recorded as supported, unsupported, or — for capabilities the probe deliberately did not exercise — unknown), and a notes section recording responses that did not match a known classification.
2. **Given** any supported device, **When** the integrator calls `probe_capabilities()`, **Then** no destructive operation is invoked: no `*/add`, `*/set`, `*/del`, no `/api/relay/trig`, and no `/fcgi/do?action=OpenDoor`. This holds even for capabilities the report cannot otherwise classify.
3. **Given** a device whose list endpoints respond, **When** the probe inspects schema, **Then** observed field-name variants for the user schedule field and the contact schema are recorded in the report so that downstream code can consult them.
4. **Given** an endpoint that returns the typo `"No hanlders for this request"`, **When** the probe classifies the response, **Then** the corresponding capability is recorded as unsupported (not as an error or as supported), and the typo is treated identically to the corrected spelling if the device ever emits it. <!-- codespell:ignore hanlders -->
5. **Given** a probe run against the same device twice in succession, **When** the integrator compares the two reports, **Then** they are equivalent — the probe is idempotent and side-effect-free.

### User Story 2 - Library knows about common devices and refuses unsupported operations clearly (Priority: P1) — Phase 2

An integrator using the library against a device class the library already knows about (X916, X915S on current firmware, E18C on current firmware, IT83) does not need to probe before making calls: the library recognises the device and pre-populates its capability profile from a curated matrix shipped in the library. When the integrator calls an operation the device does not support — for example, calling the user-add path against an IT83 indoor monitor, or calling the contact-add path against an X915S running the apartment-book schema — the call fails immediately with a clear, structured `AkuvoxUnsupportedError` that names the missing capability, the device class, and a human-readable reason. No request reaches the device. For capabilities with multiple implementations (notably relay trigger), the library dispatches to the right adapter automatically based on the matrix entry, so the integrator simply calls "open the door" and the library picks the supported underlying mechanism.

**Why this priority**: This is where users gain the visible benefit of the work: clear errors instead of cryptic device responses, and operations that "just work" on devices the library knows about. It also locks in the surfacing contract that Phase 3 then refactors the rest of the codebase onto.

**Independent Test**: Configure the library against each of the four supported device classes (X916, X915S current firmware, E18C current firmware, IT83) without explicitly probing first; for each, confirm (a) calling a supported operation succeeds, (b) calling an unsupported operation raises `AkuvoxUnsupportedError` with the missing capability and device class populated, (c) the unsupported call did not produce a network request to the device, (d) the relay-trigger operation routes to the correct underlying mechanism per device class, and (e) for any capability whose status is `unknown`, the call fails-fast by default but proceeds when `attempt_unknown_capability` is set on the device.

**Acceptance Scenarios**:

1. **Given** an X916 on `916.30.10.*` firmware, **When** the library connects, **Then** the device's capability profile is populated from the matrix without any list endpoints being probed.
2. **Given** an IT83 on `83.*` firmware, **When** the integrator calls the user-add operation, **Then** the library raises `AkuvoxUnsupportedError` identifying the missing capability and the device class, and no HTTP request is sent.
3. **Given** an X915S on current firmware whose contacts use the apartment-book schema, **When** the integrator calls the contact-add operation, **Then** the library raises `AkuvoxUnsupportedError` (because contact writes return `unsupported action` on this firmware) without sending a request.
4. **Given** an IT83, **When** the integrator calls the relay-trigger operation, **Then** the library dispatches to the `/fcgi/do?action=OpenDoor` adapter; **Given** an X916, **When** the same call is made, **Then** the library dispatches to the `/api/relay/trig` adapter.
5. **Given** any matrix entry, **When** the entry is inspected, **Then** it carries provenance metadata identifying the test-bench device, firmware version, and library version that contributed the entry.
6. **Given** an integrator who explicitly calls `probe_capabilities()` after connection, **When** the probe completes, **Then** the device's effective capability profile is updated by merging the probe result with the matrix-derived profile per the merge rule in FR-009 (probe `SUPPORTED`/`UNSUPPORTED` wins; probe `UNKNOWN` preserves any matrix-confirmed status), and subsequent calls use the refreshed profile.
7. **Given** a device whose capability profile has at least one capability with status `unknown` (e.g., a probed device that did not exercise writes, or an unrecognized device for which no matrix entry exists), **When** the integrator calls that capability's operation with `device.attempt_unknown_capability = False` (the default), **Then** the library raises `AkuvoxUnsupportedError` with `reason="capability_unknown"` and no HTTP request is sent; **When** the integrator first sets `device.attempt_unknown_capability = True` and calls the same operation, **Then** the library dispatches the call to the underlying API and any device-side error is surfaced verbatim. Capabilities whose status is `unsupported` (confirmed-negative) continue to fail-fast regardless of the override.

### User Story 3 - Existing scattered compat code consolidates onto the matrix (Priority: P2) — Phase 3

A maintainer adding support for a new device class or firmware band makes a localized change: one new entry in the capability matrix and, where the device introduces a genuinely new behavior, one or two adapters. They do not need to add conditional branches across the user model, contact model, schedule serializer, or relay client. Existing field-name aliasing — most notably the dual-write of `ScheduleRelay` and `Schedule-Relay` for E18C, the multi-name `Schedule` / `ScheduleRelay` parsing for X915S, and the schema-shape branching for apartment-book contacts — is moved out of the model classes and onto capability records that the parsers and payload builders consult at call time.

**Why this priority**: This is the structural payoff of the previous two phases. It is shippable independently because the externally observable behavior does not change: the same payloads are produced and the same fields are parsed. The benefit accrues to maintainers (and to the next firmware variant we discover).

**Independent Test**: Run the full existing test suite — including the X916, E18C, and X915S compat tests landed by issues #99 and #118 — against the refactored code with no test changes other than where tests were verifying the exact location of the conditional. All payload-shape and parse-shape assertions continue to pass.

**Acceptance Scenarios**:

1. **Given** an E18C device whose matrix entry indicates it requires the hyphenated write field, **When** the library builds an add-user payload, **Then** the payload contains the hyphenated field name and the un-hyphenated field name (matching today's behavior) without any conditional branch in the user model class — the field-name set is read from the capability record.
2. **Given** an X915S on current firmware whose matrix entry indicates the read field is `Schedule`, **When** the library parses a user list response, **Then** the schedule value is extracted via the field-name list from the capability record without the user-parser hard-coding `Schedule` / `ScheduleRelay` / `Schedule-Relay` alternatives.
3. **Given** an X915S whose matrix entry marks it as having the apartment-book contact schema, **When** the library parses a contact list response, **Then** parsing succeeds without requiring an `ID` field and without raising on the apartment-style fields, driven by the capability record's schema-shape selector. *(Read-side only: apartment-book contact WRITES are explicitly **out of scope** for this feature — see Out-of-Scope §"Apartment-book contact writes" below. On X915S, `CONTACT_ADD` is **UNSUPPORTED** in the matrix because the door-phone `add_contact` payload returns `unsupported action` on the firmware (issue #121); `CONTACT_MODIFY`/`CONTACT_DELETE` default to UNKNOWN (no hardware-bench evidence cited for those specifically). The wrapper gate raises `AkuvoxUnsupportedError(reason="capability_missing")` on ADD without ever reaching the payload-shape switch. An apartment-book-shaped write would be a separate, currently-unscoped capability variant — the Phase 3 `schema_shape=SchemaShape.APARTMENT_BOOK` write path raises `NotImplementedError` with a deferral message pointing to a follow-up issue, but only surfaces if the caller has set `attempt_unknown_capability=True` AND somehow reached a capability whose status is UNKNOWN.)*
4. **Given** a maintainer adding support for a hypothetical new firmware band, **When** they add a single matrix entry, **Then** that entry alone is sufficient to control field-name aliasing, schema-shape selection, and adapter dispatch for that device — no edits to model classes are required for known-shape variations.

### User Story 4 - Documentation and MVP example reflect supported capabilities (Priority: P3) — Phase 4

A new user who reads the library's documentation finds a "Device support matrix" page enumerating the known device classes, the firmware bands they are confirmed against, and the capabilities each supports — kept in sync with the in-library matrix. The MVP example script (`examples/mvp_test.py`) probes the device once at startup and then runs only the operations the device supports, marking the rest as skipped with the reason from the capability record. The user is no longer surprised by mid-script failures on devices that lack a given capability.

**Why this priority**: This is the user-experience polish that turns the architectural work into something contributors and integrators can actually find. It depends on Phases 1–3 being in place but is independent of any further library behavior.

**Independent Test**: Run `examples/mvp_test.py` against each of the four supported device classes; confirm (a) the script begins by probing capabilities, (b) operations the device does not support are skipped with a clear message rather than attempted-and-failed, (c) the documentation page lists each device class and its capabilities and matches what the library actually exposes for that class.

**Acceptance Scenarios**:

1. **Given** a contributor reviewing supported devices, **When** they consult the documentation, **Then** they find a device support matrix page listing each known device class, firmware band, and supported capabilities, with a note on how to add new entries.
2. **Given** the MVP example script, **When** it runs against an IT83, **Then** the user-add and contact-add steps are reported as "skipped: status unknown on this device class" (the matrix leaves IT83 writes as `UNKNOWN` because no concrete UNSUPPORTED evidence exists for those endpoints; #122/#130 evidence is `/api/relay/*` "No handlers" — `RELAY_API_TRIG` only) rather than attempted, and the relay-trigger step succeeds via the FCGI adapter (matrix-confirmed `RELAY_TRIGGER_FCGI = SUPPORTED`).
3. **Given** the documentation page and the in-library matrix, **When** they are compared, **Then** every device class in the matrix appears in the doc page and vice versa.

### Edge Cases

- **Probe encounters the typo `"No hanlders for this request"`**: classified identically to the correctly-spelled `"No handlers for this request"`. Both indicate the endpoint is not registered on the device; the corresponding capability is recorded as unsupported. <!-- codespell:ignore hanlders -->
- **Probe encounters `retcode: -1, message: "unsupported action"`**: the endpoint is present but the requested action is rejected. The *read* capability covered by that endpoint is recorded as `supported` (the endpoint exists; the read action was honoured) and the raw response is recorded under a keyed `DeviceCapabilities.notes[...]` entry (e.g. `notes["contact_get_body"]`) for maintainer review. Per FR-003, the corresponding *write* capability remains `unknown` — the probe MUST NOT infer write status from a read-endpoint signal; only curated matrix entries promote write capabilities to `supported` or `unsupported`.
- **Probe encounters HTTP 500**: classified as "unknown firmware behavior — recorded but not used to set capability flags". The corresponding capability's status is recorded as `unknown` (not `supported`, not `unsupported`), and the notes section preserves the response so a maintainer can later decide whether to add a quirk annotation. (This is the X915S `2915.30.10.113` shape from #119.) HTTP 500 is genuinely indeterminate — the three-valued capability-status model exists precisely to represent this case without inventing false positives or false negatives.
- **Probe encounters HTTP 401 or HTTP 403 on step 1** (`/api/system/info`): classified as caller-side authentication failure, not a capability signal. The probe aborts cleanly with an authentication error after 1 call — without credentials, classifying the remaining capability surface is meaningless. **Probe encounters HTTP 401 or HTTP 403 on a later step** (steps 2–9): the affected capability is recorded as `unknown` with a status-code note, and the probe continues — a successful step 1 already established that credentials are valid, so a per-endpoint 401/403 reflects per-endpoint ACL rather than session-wide auth failure.
- **Network or transport-level failure during probe** (timeout, connection refused, DNS): the probe surfaces the underlying transport error rather than fabricating a capability report; capability inference requires successful HTTP responses.
- **Unknown-device first contact**: if a device does not match any matrix pattern, the library's behavior is conservative — operations that have not been confirmed for this device raise `AkuvoxUnsupportedError` with a reason indicating the device is unrecognized, and the integrator is directed to call `probe_capabilities()` explicitly. The library does not silently auto-probe on first call (auto-probing would surprise integrators with extra round-trips).
- **Probe results vs. matrix defaults**: when both are present, the per-capability merge follows the 9-cell table in `contracts/probe-api.md` §"Edge cases" item 7. Probe `SUPPORTED` and `UNSUPPORTED` win as newer first-hand evidence; probe `UNKNOWN` preserves a matrix-confirmed status (so transient probe indeterminacy — e.g. an HTTP 500 on a read endpoint the matrix knows to be supported — cannot degrade curated knowledge). Capabilities the probe did not exercise carry through unchanged from the matrix.
- **Provenance staleness (firmware update invalidates a matrix entry)**: matrix entries record the test-bench device and firmware version that contributed them. When a firmware update changes capabilities, the integrator sees a probe-vs-matrix mismatch they can report; the library does not auto-update the shipped matrix from probe results in production.
- **Field-name alias collision**: where a single device responds to multiple field names for writes (e.g., E18C accepts both `Schedule-Relay` and `ScheduleRelay` if both are sent), the matrix entry's write-field list controls which names are emitted; reads consult the read-field list in order and use the first present.
- **Adapter dispatch with no matching adapter**: if the matrix indicates a capability is supported but no adapter is registered for the device's variant of it (e.g., a new endpoint shape we haven't implemented yet), the call raises `AkuvoxUnsupportedError` with a reason that distinguishes "device cannot do this" from "library does not yet implement this for this device class".

## Requirements *(mandatory)*

### Functional Requirements

#### Capability model and probe (Phase 1)

- **FR-001**: The library MUST define a discrete, enumerable set of logical capabilities covering the operations it currently exposes — at minimum: user list / add / modify / delete; schedule list / add; group list / add; contact list / add; the apartment-book contact schema variant; relay trigger via the `/api/relay/trig` path; relay trigger via the `/fcgi/do?action=OpenDoor` path; relay status; device-config get / set; door log; call log; key discovery. The enumeration MUST be extensible without breaking existing callers.
- **FR-002**: The library MUST define a `DeviceCapabilities` data structure carrying, at minimum: detected device class, detected firmware version, a per-capability status profile (each known `Capability` mapped to `supported`, `unsupported`, or `unknown` — the three-valued model that distinguishes confirmed-negative evidence from absence of evidence), observed field-name aliases per logical field (read names and write names), observed schema shapes per resource, a freeform notes record for unclassified responses, and provenance metadata identifying how the record was produced. A convenience view exposing only the `supported`-status entries as a set MUST be provided for callers that do not need to distinguish `unsupported` from `unknown`.
- **FR-003**: The library MUST expose `await device.probe_capabilities()` returning a `DeviceCapabilities`. The probe MUST be non-destructive: it MUST NOT call any `*/add`, `*/set`, `*/del`, `/api/relay/trig`, or `/fcgi/do?action=OpenDoor` endpoint regardless of how the device responds, and MUST NOT depend on test data existing on the device. As a direct consequence of non-destructiveness, **the probe MUST NOT infer any non-`unknown` status for write capabilities** (`*_ADD`/`*_MODIFY`/`*_DELETE`/`DEVICE_CONFIG_SET`/`RELAY_TRIGGER_*`). Probe-derived write capabilities are always `unknown`. In particular, a read endpoint returning the `"unsupported action"` envelope is recorded in `DeviceCapabilities.notes` and may classify the corresponding *read* capability, but MUST NOT propagate to the write counterpart — read and write endpoints are independently routed on observed devices, and one's rejection envelope is not evidence about the other. Only curated matrix entries (FR-006, FR-007), populated from hardware-bench observation of actual write attempts, may promote a write capability to `supported` or `unsupported`.
- **FR-004**: The probe MUST classify endpoint responses against the well-known failure-shape strings (`"No handlers for this request"`, the typo variant `"No hanlders for this request"`, `"Api unsupported"`, and `"unsupported action"`) consistently and document this classification publicly. HTTP 500 MUST be recorded but MUST NOT be treated as a capability signal. **HTTP 401/403 on step 1** (the `/api/system/info` device-class probe) MUST abort the probe with an authentication error after that single call. **A step-1 HTTP 2xx response whose body fails to parse to `DeviceInfo`** (malformed JSON, missing required device-class fields) MUST also abort the probe — with `AkuvoxParseError` after exactly that single call — because subsequent steps depend on the `DeviceInfo` for device-class identification and notes population, and continuing without it would produce a half-built profile that contradicts the no-partial-profile guarantee in FR-005. **HTTP 401/403 on a later step** (steps 2–9) MUST record the affected capability as `unknown` with a status-code note and MUST NOT abort — the probe continues and still totals 9 calls. See `contracts/probe-api.md` §"Step-1 failure modes" for the complete enumeration. <!-- codespell:ignore hanlders -->
- **FR-005**: The probe MUST be idempotent: invoking it twice in succession against the same device MUST produce **byte-equal** `DeviceCapabilities` objects (`assert a == b`). No timestamp or wall-clock state is written into the probe output (per `contracts/probe-api.md` §"Idempotence" + §"Provenance produced by the probe": probe-derived profiles carry `provenance=None` and no `probed_at`-style note in `notes`).

#### Capabilities matrix and surfacing (Phase 2)

- **FR-006**: The library MUST ship a curated capabilities matrix mapping device-class-and-firmware patterns to `DeviceCapabilities` records. At minimum the matrix MUST cover X916, X915S on current firmware, E18C on current firmware, and IT83 — the four supported device classes with hardware available for verification.
- **FR-007**: Each matrix entry MUST record provenance identifying the test-bench device, firmware version, and library version that contributed the entry, so staleness is observable when firmware changes.
- **FR-008**: When a device matches a matrix entry on first contact, the library MUST populate that device's effective capability profile from the matrix without invoking the probe — so existing integrators on supported hardware do not pay an extra round-trip.
- **FR-009**: When an integrator explicitly calls `probe_capabilities()`, the resulting `DeviceCapabilities` MUST be merged with any matrix-derived profile for the lifetime of that connection per the 9-cell merge table in `contracts/probe-api.md` §"Edge cases" item 7 (reproduced in `contracts/matrix-lookup.md` §"Probe-vs-matrix interaction"). The governing rule: probe `SUPPORTED` or `UNSUPPORTED` takes precedence over any matrix value (newer first-hand evidence); probe `UNKNOWN` MUST NOT regress a matrix-confirmed `SUPPORTED` or `UNSUPPORTED` status (absence of evidence is not evidence of absence — transient probe indeterminacy must not degrade curated knowledge); capabilities the probe did not exercise carry through unchanged from the matrix.
- **FR-010**: The library MUST expose a public `AkuvoxUnsupportedError` carrying structured information including the missing capability, the detected device class, and a human-readable reason.
- **FR-011**: Every operation on the public device API that exercises a device capability MUST consult the effective capability profile and raise `AkuvoxUnsupportedError` immediately when the underlying capability's status is `unsupported` (confirmed-negative) — without sending an HTTP request to the device. By default, capabilities with status `unknown` MUST also raise `AkuvoxUnsupportedError` immediately (fail-fast on unproven capabilities); see FR-021 for the integrator opt-in that lets `unknown`-status capabilities be attempted. **Explicit out-of-scope** (infrastructure methods, not service-operation methods): `AkuvoxDevice.get_info()`, `AkuvoxDevice.get_status()`, and `AkuvoxDevice.probe_capabilities()` are NOT capability-gated because (a) `get_info()` / `get_status()` run before matrix lookup (the probe itself depends on them) and the underlying `/api/system/info` and `/api/system/status` endpoints are universally available on every Akuvox device, and (b) `probe_capabilities()` is the method that CREATES the effective capability profile — it cannot gate itself behind a capability check (chicken-and-egg). See `data-model.md` §"Explicit out-of-scope" for the full list, rationale, and the adapter-gated exception for `trigger_relay()`. Every other public service-operation coroutine method on `AkuvoxDevice` is gated.
- **FR-012**: For capabilities with multiple implementations (notably relay trigger via `/api/relay/trig` versus `/fcgi/do?action=OpenDoor`), the library MUST dispatch to the correct adapter based on the device's effective capability profile. Callers MUST be able to override the dispatch decision when they have explicit reason to.
- **FR-013**: Devices that do not match any matrix pattern MUST behave conservatively: operations that have not been confirmed for the device raise `AkuvoxUnsupportedError` indicating the device is unrecognized and directing the caller to `probe_capabilities()`. The library MUST NOT silently auto-probe on first call.

#### Refactor field-name aliasing and schema shape onto the matrix (Phase 3)

- **FR-014**: Field-name aliasing for the user schedule field — currently producing both `ScheduleRelay` and `Schedule-Relay` on writes and accepting `ScheduleRelay` / `Schedule-Relay` / `Schedule` on reads — MUST be driven by the device's capability record (write-field list and read-field list). Model classes MUST NOT hard-code these alternatives.
- **FR-015**: Contact schema selection between the door-phone shape and the apartment-book shape (extra `APTName`, `APTNum`, `Building`, `Landline` fields, no `ID`) MUST be driven by the capability record. The contact parser MUST NOT raise on missing `ID` when the capability record indicates the apartment-book schema.
- **FR-016**: After the refactor, the externally observable payload shapes and parse results MUST be unchanged for every device the library currently supports. Existing tests covering #99 / PR #101 (E18C dual-write) and #118 / PR #120 (X915S `Schedule` read) MUST continue to pass.
- **FR-017**: Adding support for a new device class or firmware band whose variation is limited to **known axes that have library-side machinery already in place** (endpoint availability, read-side field-name aliasing, read-side schema shape, action availability via existing adapter dispatch) MUST be possible by adding a single matrix entry without editing model classes, parsers, or payload builders. *Variations that require new library machinery (e.g. apartment-book contact WRITE payloads, which need both an API-design step to source the `APTName`/`APTNum`/`Building`/`Landline` fields and hardware-bench write evidence — see Out-of-Scope §"Apartment-book contact writes") are explicitly NOT covered by this FR and require follow-up issues.*

#### Documentation and MVP integration (Phase 4)

- **FR-018**: The library MUST publish a "Device support matrix" documentation page listing each known device class, firmware band, and supported capabilities, kept in sync with the in-library matrix. The page MUST include guidance for contributing a new entry.
- **FR-019**: The MVP example script (`examples/mvp_test.py`) MUST call `probe_capabilities()` at startup and use the result to skip or mark-unsupported any step whose capability is absent, rather than attempting the call and catching the resulting error. Skipped steps MUST be reported with a clear reason; the report MUST distinguish capabilities whose status is `unsupported` ("not supported on this device class") from capabilities whose status is `unknown` ("status unknown on this device class — add a matrix entry or set `attempt_unknown_capability=True` to probe").
- **FR-020**: The library MUST ship tests exercising the probe and the capability surfacing against mocked responses representing each of the four supported device classes (X916, X915S, E18C, IT83), including the well-known failure shapes from FR-004.

#### Integrator opt-in for unknown-status capabilities (Phase 2)

- **FR-021**: Integrators MUST be able to opt into attempting operations whose capability status is `unknown` via an explicit per-device override (e.g., `device.attempt_unknown_capability = True`). When this override is set, an `unknown`-status capability MUST be dispatched to the underlying API, and any device-side error MUST be surfaced verbatim to the caller (the library MUST NOT translate the device's error into a capability error in that mode). The default value of the override MUST be `False` — `unknown`-status operations raise `AkuvoxUnsupportedError(reason="capability_unknown", ...)` without a network round-trip. The override exists so users of unfamiliar devices can deliberately probe write capabilities and contribute observations back to the matrix; it is not a substitute for adding matrix entries. Capabilities whose status is `unsupported` (confirmed-negative evidence) MUST continue to fail-fast regardless of the override's value.

### Key Entities

- **Capability**: a discrete, enumerable identifier for one logical operation (e.g., "list users", "add user", "trigger primary relay via the API path", "trigger primary relay via the FCGI path", "use apartment-book contact schema"). Capabilities are the unit whose status is tracked in a `DeviceCapabilities` record (each `Capability` is `supported`, `unsupported`, or `unknown` for a given device).
- **CapabilityStatus**: the three-valued status of a single capability on a single device — `supported` (positive evidence: matrix entry or successful probe), `unsupported` (positive negative evidence: matrix entry or probe-classified failure shape), or `unknown` (no evidence either way: probe did not exercise it and no matrix entry covers it). The three-valued model exists so that operations the library has not confirmed can fail-fast with a clear "status unknown" message rather than be attempted and produce a cryptic device-side error.
- **DeviceCapabilities**: the record describing one device's effective capability profile. Carries device class, firmware version, the per-capability status profile (each known `Capability` mapped to a `CapabilityStatus`), field-name aliases (per logical field, read and write), schema shapes (per resource), unclassified-response notes, and provenance metadata. Produced by the matrix or by the probe. Exposes a convenience view (`supported_set`) returning the keys whose status is `supported` for callers that do not need the three-valued distinction.
- **DeviceClassPattern**: the matrix key — pairs a model-prefix pattern with a firmware-band pattern (including band-floor matchers like `"2915.30.10.114+"`). Determines which `DeviceCapabilities` record applies to a given device.
- **Capability matrix**: the curated, in-library mapping from `DeviceClassPattern` to `DeviceCapabilities`. Manually maintained; not auto-updated from probe results in production.
- **Capability adapter**: the implementation chosen at call time for a capability that has multiple variants on different devices (e.g., `/api/relay/trig` vs. `/fcgi/do?action=OpenDoor` for relay trigger).
- **AkuvoxUnsupportedError**: the structured exception raised when an operation's capability is missing on the connected device. Carries capability, device class, and reason.
- **Provenance metadata**: per-matrix-entry record of the test-bench device, firmware version, and library version that contributed the entry. Used by maintainers to recognize staleness when firmware changes.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A non-destructive probe is available: `probe_capabilities()` against any of the five evidence devices (X916 916.30.10.114, E18C 18.30.11.21, X915S 2915.30.10.114 current, X915S 2915.30.10.113 historical, IT83 83.30.10.4) completes without invoking any of `*/add`, `*/set`, `*/del`, `/api/relay/trig`, or `/fcgi/do?action=OpenDoor`. ## Phasing

The four user stories above correspond to the four-phase split called out in issue #123. Each phase is independently shippable and delivers user-visible value on its own:

1. **Phase 1 — Capability model and probe** (User Story 1): introduces the `Capability` enum, the `DeviceCapabilities` data structure, and `probe_capabilities()`. No behavior change for existing callers; the probe is opt-in.
2. **Phase 2 — Matrix, dispatch, and `AkuvoxUnsupportedError`** (User Story 2): introduces the curated matrix, populates each connection's effective profile from the matrix, raises `AkuvoxUnsupportedError` for `unsupported` and (by default) `unknown`-status capabilities, adds adapter dispatch for relay trigger, and exposes the `attempt_unknown_capability` integrator opt-in (FR-021). Is the first phase that changes the public-facing behavior.
3. **Phase 3 — Refactor existing aliasing and schema-shape branches onto the matrix** (User Story 3): moves field-name alias lists and contact-schema-shape selection out of the model classes onto capability records. Externally a no-op; internally consolidates the compat code paths.
4. **Phase 4 — Documentation and MVP example integration** (User Story 4): publishes the device support matrix doc page and updates `examples/mvp_test.py` to probe-then-run-supported-only.

## Out of Scope

The following items are explicitly out of scope for this feature, taken from issue #123:

- Per-firmware **bug** workarounds beyond field-name and schema variation. The X915S `2915.30.10.113` HTTP-500 case is a firmware bug, not a capability — it is recorded as an annotated quirk in the matrix at most, not modeled as a first-class capability.
- Web-UI auth and `/web/*` endpoints. The matrix scope is HTTP API plus `/fcgi/*` only.
- **Auto-update of the matrix from probe results in production.** The matrix is curated; probes inform manually-authored entries. The library will not silently mutate the shipped matrix based on what a runtime probe sees.
- **Reason-code granularity for unrecognized devices.** The implementation MAY collapse the `device_unrecognized` reason (used when a device matches no matrix pattern) and the `capability_unknown` reason (used when a specific capability has `unknown` status) into a single reason, if Phase-2 implementation finds the distinction not useful in practice; both surface identical caller-facing UX (fail-fast with a message directing the integrator to add a matrix entry or set `attempt_unknown_capability=True`). Whichever choice the implementation makes is internal and not constrained by this spec.
- **Apartment-book contact writes (`schema_shape=SchemaShape.APARTMENT_BOOK` on `add_contact`/`modify_contact`).** Phase 3 ships read-side apartment-book parsing only (per US3 acceptance §3 and FR-015). Apartment-book WRITE payloads are deferred to a follow-up issue because (a) the current public `add_contact(name, phone, group)` / `modify_contact(id, name, phone, group)` signature has no source for the required `APTName`/`APTNum`/`Building`/`Landline` fields and (b) no hardware-bench evidence exists that X915S or IT83 contact writes succeed in an apartment-book shape — the existing door-phone shape is empirically rejected on X915S (`CONTACT_ADD = UNSUPPORTED` in the matrix, from issue #121's `unsupported action` evidence) and untested on IT83 (UNKNOWN). The Phase 3 service-function `schema_shape=SchemaShape.APARTMENT_BOOK` code path raises `NotImplementedError` with a deferral message; the wrapper-level capability gate (matrix-marked `UNSUPPORTED` for X915S ADD; `UNKNOWN` for IT83 and for X915S MODIFY/DELETE) is the first line of defense and `UNSUPPORTED` always blocks regardless of `attempt_unknown_capability`. The `NotImplementedError` only ever surfaces to callers who explicitly set `attempt_unknown_capability=True` AND reach a capability currently in `UNKNOWN` state. The follow-up work needs both an API-design step (how to expose apartment-book write fields ergonomically) and at least one hardware-bench apartment-book write attempt to confirm the payload shape.

## Dependencies and Assumptions

- **Models layout**: domain models live at `src/pylocal_akuvox/models/` (post-#126 / spec 007 split — seven domain submodules plus a compatibility shim). The capability module is a cross-cutting concern and lives outside the per-domain submodules at `src/pylocal_akuvox/capabilities.py` (per the merged spec 007 data-model.md cross-cutting note).
- **Existing aliasing locations**: today, `User.from_api_response` accepts `ScheduleRelay` / `Schedule-Relay` / `Schedule`, and the user write payload dual-writes `Schedule-Relay` for E18C (#99 / PR #101). Phase 3 moves these field-name lists onto capability records but does not change the externally observable payloads or parses for currently-supported devices.
- **MVP example evolution**: a separate parallel work stream is enriching `examples/mvp_test.py` with diagnostics. Phase 4 of this feature integrates `probe_capabilities()` into whatever shape `mvp_test.py` has at that point — this feature does not redesign the example beyond the probe-and-skip behavior.
- **Hardware availability**: the maintainer has access to A08S, X915S, X916, and E18C; IT83 verification is via the community reporter from tykeal/homeassistant-local-akuvox#130. Matrix entries for the four supported device classes are populated from hardware-bench observation; entries for hypothetical or community-reported devices are not in scope here.
- **Vendor documentation**: where the Akuvox vendor docs index (https://knowledge.akuvox.com/llms.txt) confirms an endpoint or schema shape, that confirmation is recorded in the matrix entry's notes; the matrix is otherwise grounded in observed device behavior, not in vendor documentation alone.
- **Folded issues**: #118 (closed — `Schedule` read variant) and #119 (closed — X915S firmware HTTP 500) are folded for design lineage; their resolutions are absorbed into the matrix and the probe's HTTP-500 classification respectively. #121 (open — apartment-book contact schema) and #122 (open — IT83 FCGI relay) are folded as in-scope facets to be closed by this feature's matrix entries and adapter dispatch.
